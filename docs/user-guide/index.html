pdo User Guide

pdo runs a team of coding agents on a GitHub project. Agents take issues, write the code, test it and open pull requests. People decide what gets built, answer questions, review what users will see, and merge. All of it is tracked and managed in GitHub issues, labels, the project board and pull requests. This guide covers the human side: what to do, where to do it, and what the labels mean.

The whole thing in one list

How work moves

Every issue follows the same path. Amber numbers are steps where a person acts. For the full flowchart, every skill's steps and the sub-agents each one spawns, see the Workflow Deep Dive.

  1. Anyone · intake agentAn idea or bug becomes an issue.Intake drafts a typed issue with a priority and route, checks for duplicates, and files it only after a person says OK.
  2. Intake · ownerIt gets a priority.Usually set during intake: the draft suggests a P1–P4 label and the owner confirms it, or the owner adds one later. The labels order the queue, and the board's "Claude Work This" status jumps an issue to the front.
  3. OrchestratorAn agent is started.When a slot is free, the orchestrator claims the issue with a managed-by: label and starts one command agent in its own copy of the code, as a new tab in the project's herdr workspace.
  4. Command agent · ownerThe agent builds it and asks when unsure.It explores, plans, builds, has its work reviewed by a panel of reviewer subagents, and opens a PR. Questions go straight to the owner.
  5. Command agentThe PR is marked ready for QC.It carries a QC checklist and links any test data. The agent then hibernates to free memory; it keeps its full context.
  6. QC Agent (if the project runs one)An agent tests it first.Failures go back to the same command agent, which fixes them. A pass decides whether a person needs to look.
  7. Reviewer or ownerA person reviews what users will see.Feedback wakes the agent, which fixes and re-labels. A pass marks the PR Ready for Merge.
  8. OwnerA person merges.Always. Agents never merge. The finished agent closes and releases its claim on its own.

Three routes: small, design, build

Step 3 starts the agent on one of three lifecycles, chosen by the issue's route: label. Intake suggests the route and the owner can change it. Most work is small. Big features take two trips: a design trip that produces a plan and no code, then a build trip that turns the plan into one PR.

route:small

Small fix or feature

For
Bugs, tasks and single features that fit one agent's working memory and have no open design questions.
Skill
/project-small-feature-or-bug-fix
Steps
Explore the code, ask what's ambiguous, plan, build in its own worktree, test, write the QC checklist and changelog, open the PR, one review-and-fix cycle.
You
Answer questions while it builds; QC and merge the PR.
Result
One PR at ready for QC.

If it turns out to need a migration or a cross-cutting UX decision, the agent stops and asks to be re-routed to design.

route:design

Design a big feature

For
Epics, cross-cutting work, and anything with open UX or architecture choices (also anything labelled needs-design).
Skill
/project-feature-design
Steps
Survey the code, past issues and notes; write a proposal; a panel of reviewer agents challenges it; then one decisions gate with you.
You
Make the key decisions in one sitting, each with a recommended answer.
Result
A design doc committed to the repo, with a phased delivery plan and the UX checkpoints, plus a GitHub epic with one epic-phase sub-issue per phase. No product code.

When the doc is marked READY, the orchestrator starts the build on its own.

route:build

Build from the design

For
An epic whose design doc is READY.
Skill
/project-feature-build
Steps
Works every phase in order inside one PR, one commit per phase. Each phase gets a compile check, a fresh-eyes review, headless QC and a verifier, and is recorded in a progress ledger and its phase issue.
You
Try working prototypes at the UX checkpoints the design set (awaiting-ux-gate; the agent frees its slot while it waits), then QC and merge.
Result
One PR for the whole epic at ready for QC.

Phase issues are never started on their own; only the epic's build agent works them.

You review prototypes, never design docs.The design trip asks you only the decisions it can't make. Everything else you see is running software: prototypes at UX checkpoints, then the finished PR.
Where work is tracked

Everything lives on GitHub

pdo has no tracker of its own. Every issue, priority, claim, PR and QC verdict is on GitHub, so anyone with access to the repo can see where things stand without asking an agent or the owner. Agents read and write the same issues, labels and comments you do.

LabelsPriority (P1–P4), route, claim (managed-by:), QC state, UX review.The label reference says what each one means and who sets it.

What stays off GitHub is machine-local: each agent's saved conversation, its working copy of the code, and the engine's own records. None of it is needed to follow the work.

Role · owner

Running the team

You run the engine on one machine. You talk to one session, the CEO. It starts each project's lead, the Repo Manager, and the Repo Manager runs that project's team. Changes to the engine itself go to a separate session, the System Manager.

You need herdr to run the team.herdr is the terminal workspace manager the team lives in. Each project gets one herdr workspace, its home, and every agent of that project is a named tab in it. The engine uses herdr to start, watch, prompt and hibernate those agents, and herdr's status (working, idle, blocked) is how the orchestrator and you know who is waiting. Install it before setup, then open your CEO session inside herdr. You only need herdr to run the team: collaborators with their own agent don't need it.

First-time setup

The engine ships inside the plugin, so the plugin is the only thing you install.

  1. Install the plugin (the same commands as in Working with your own agent).
  2. Open your agent in the repo the team will work and run /project-setup repo+team. It installs the engine from the plugin as pdo (it always runs the newest plugin version, so updating the plugin updates the engine), checks the requirements (bash 4+, python 3.8+, git, jq, the GitHub CLI and herdr), registers the repo, and opens one PR with the files every agent reads (AGENTS.md, .agents/project-profile.md) and a human guide (docs/agent-workflow.md). Merge it.
  3. Install anything the requirements check said was missing, then start the team (next section).

Run /project-setup repo+team again in each further repo; it only fills gaps. To develop the engine itself or pin a version, clone binerbuddy/project-dev-orchestration and run bin/install --bin from the checkout instead.

Start the team

In herdr, open a workspace named CEO, start Claude Code there with claude -n CEO, and type:

/pdo:ceo fire up acme

The CEO opens the acme workspace with Repo Manager (acme) in tab 1 (pdo start-manager) and asks it to start the team. The Repo Manager starts whatever is missing: intake, Human Review, the QC Agent (if configured), the orchestrator and any project extras, each as a tab. Then the CEO reports. Use the same command after /clear or in a new session; it never starts anything twice.

One machine, one CEO. With several projects it gives you a single "waiting on you" list across all of them, watches the shared limits (usage, memory, disk, GitHub calls), and pauses the projects you aren't working on.

Stopping and restarting

pdo shutdown --project acme shows what it would stop (the orchestrator and its watcher, the command agents, Human Review and the QC Agent with their served apps, then the Repo Manager). Add --apply to do it; --all stops every project and intake too. Command agents are hibernated, not lost: their conversations, branches and claims stay, and each resumes where it stopped. It never touches the CEO, the System Manager or your own sessions, and skips any tab with a question waiting. Fire the project up again to restart.

Answering agents

Agents ask in their own tab, named <Repo>-<issue#> <brief>, in the project's home. herdr marks a waiting agent as blocked, and Remote Control mirrors every session to claude.ai and the phone app, so you can answer from anywhere. A question about business rules that could change results is a blocking gate: the agent waits for your explicit approval.

Filing bugs and ideas

  • Your own: in the intake workspace type /project-intake <what you saw or want>. It checks for duplicates, shows you a draft, and files after one OK. Say it's urgent and it can go straight to Claude Work This.
  • From agents: agents never file on their own. They drop reports in the intake inbox. Run /project-intake inbox when you have time to triage the batch, or name a single report to work just that one.
  • One intake session and one inbox serve every project on the machine; each report records which agent sent it.

Human review on your machine

In the Human Review (<project>) tab, run /project-human-review <PR#> (or ask the CEO to QC PR #<n>). It serves the PR on your reserved QC ports with its own database copy. Type what you find in plain words: it posts "QC feedback (round N)" on the PR and wakes the PR's agent. Say pass when it's good.

Where the project runs a QC Agent, it tests every ready for QC PR before you do, and only hands you the ones with visible changes. Two failed rounds add QC escalated, and the PR waits for your call.

The System Manager

The System Manager builds and repairs the engine: its scripts, skills and config. It doesn't run teams. You rarely open it yourself: ask the CEO for an engine change and it hands the work over. Open it directly (claude -n "System Manager", then /project-system-manager) when the machinery itself is broken, such as a watcher that won't run or QC that won't serve.

Several GitHub accounts

GitHub's CLI has one active account for the whole machine, so never run gh auth switch while agents are working: it breaks every other session. List which login works which owner in ~/.config/project-dev-orchestration/gh-identities and run pdo install --gh-identities. From then on every gh and git call uses the right login automatically.

When something looks wrong

  • Ask the CEO for status, then describe what you see.
  • An agent shown as "blocked" is waiting on you. Open its tab or use Remote Control.
  • Resuming an agent is always safe; it comes back with the same conversation.
  • If the engine itself misbehaves, tell the System Manager. Traps already found are written down in the engine's docs/lessons-learned.md.
Role · reviewer

Reviewing PRs

You need a browser and access to the GitHub repo. Nothing to install.

Find your work

PRs waiting for you carry QC complete - ready to review (agent QC passed, your UX review is next) or ready for QC (where no QC Agent runs). Each has one comment headed QC Checklist: steps to try in the running app, using names you'll see on screen. When the seed data doesn't cover a case, the first item links a test file to import from the repo's qc-fixtures branch.

Give feedback or pass

You want toDo this
Report a problem or answer the agentSubmit a PR review with Request changes. The PR's agent wakes up, fixes, pushes, replies on the PR, and puts ready for QC back.
Pass QCAdd the Ready for Merge label and remove QC complete - ready to review / ready for QC.
Something isn't clearAsk in the review. Agents answer on the PR, not only in their session.

Only reviews from the repo's owners, members and collaborators count. GitHub won't let you request changes on a PR you opened yourself; in that case tell the agent in its session.

Role · collaborator

Working with your own agent

You work on a repo that uses pdo with your own agent on your own machine. You don't need the orchestrator, herdr, or any engine scripts. Read the repo's docs/agent-workflow.md too; where it and this guide disagree, the repo's guide wins.

Install the whole plugin, not single skills; they share reference files. In Claude Code the skills appear as /pdo:project-<name>. After an update, start a new session (or run /reload-plugins) so the agent loads it.

First time in a repo

  1. Clone it and start your agent in the clone. It reads AGENTS.md and .agents/project-profile.md for you.
  2. It asks once whether you've read the repo's guide and offers a 3-line summary. After you say yes it won't ask again unless the guide changes.
  3. If the repo isn't set up yet, run /project-setup repo-only. It opens a setup PR for a maintainer to merge.

Only take issues a maintainer gave you, or ask first. Leave alone anything assigned to someone else, labelled managed-by:<manager> (ask that manager), or shown by GitHub as "blocked by" an open issue.

The rules your agent follows

  • Works in its own branch and worktree, passes the repo's checks, opens a PR with Closes #<n>, and stops at ready for QC.
  • Stops its dev servers and browsers before handing off, and never uses the ports reserved for QC.
  • Files out-of-scope problems instead of fixing them in passing.
  • Puts QC test data on the qc-fixtures branch, never on the PR branch.
  • Asks you before writing anything in another repo. Reading is fine.
  • Never switches the machine's GitHub account; it pins a login per command.
For everyone

Never do these

Let an agent merge. People merge, always.
Pass QC without doing it. Ready for Merge means QC really happened: a person checked, or the QC Agent tested the PR and found no visible change (it adds UX testing skipped to say so).
Set priorities you don't own. File with needs-triage; maintainers prioritise.
Type into another person's agent. Use PR comments and reviews, or ask its owner.
Start a claimed issue. A managed-by: label or an assignee means someone has it.
Run gh auth switch on a machine where agents are running.

Yellow means it's your move. Glossary

pdo
project-dev-orchestration: the skills (for any agent) plus the engine scripts (for whoever runs the team).
CEO
The first session the owner opens, one per machine. It starts, pauses and coordinates every project's team and keeps one "waiting on you" list. It never does project work.
Repo Manager
A project's lead, in tab 1 of its home: "Repo Manager (acme)". It runs that project's orchestrator, Human Review and QC Agent on the owner's and the CEO's direction.
Home
A project's herdr workspace, labelled with its name. Every agent of the project is a tab in it.
Command agent
The agent that owns one issue, from exploring to a PR ready for QC, then the wrap-up.
Orchestrator
The always-on agent that ranks the queue, starts command agents and routes events. It never writes product code.
Human Review
The tab that serves a PR on the owner's machine for a person's own QC or UX review (/project-human-review).
QC Agent
An agent that tests each PR before people do, on its own ports and data.
System Manager
The session that builds and repairs the engine: scripts, skills and config. It doesn't run teams.
Intake
The agent that turns reports into well-formed issues, after a person approves the draft. One serves every project.
Claim
The managed-by: label and comment that mark an issue as taken by one manager's agents.
Claude Work This
The board status that puts an issue at the front of the queue.
Spawn floor
The lowest priority allowed to start on its own.
Route
Which lifecycle an issue follows: small (one pass), design (a design doc first) or build (from a ready design).
Worktree
A separate copy of the repo on disk, one per agent, so agents never touch each other's files.
Hibernate
Closing an idle agent's tab to free memory while keeping its conversation, so it can be resumed later with full context.
Wrap-up
The agent's last pass after QC: final fixes, push and a closing comment. Then it closes on its own.
Fixture
Test data for QC, kept on the never-merged qc-fixtures branch and linked from the checklist.
herdr
The terminal workspace manager the agents run in: one workspace per project, one named tab per agent.
Remote Control
Claude Code's link that mirrors a session to claude.ai and the phone app.

FAQ

Do I need the engine to contribute?

No. Install the plugin for your agent tool and follow the collaborator section. The engine is only for whoever runs the team.

Which agent tools work?

Claude Code, Codex and Grok Build all load the skills. The engine launches Claude Code today.

Can an agent merge once QC passes?

No. People merge, always.

My agent found an unrelated bug. Should it fix it?

No. It files it (a needs-triage issue, or a report to the intake inbox where the engine runs) and stays on task.

Where does QC test data go?

On the repo's never-merged qc-fixtures branch, linked from the PR's QC checklist. Never on the PR branch, or it would merge with the PR.

My agent keeps asking whether I've read the guide.

It should ask once per clone and record your answer in .agents/local/guide-ack. If it asks every time, check that the file exists and that nothing cleans .agents/local/ away.

An agent disappeared. Did I lose its work?

No. Idle agents hibernate to save memory, and their work is on the branch and the PR. Ask the project's Repo Manager to bring it back; it resumes the same conversation.

Do I talk to the CEO or the Repo Manager?

The CEO for anything across projects or for starting and stopping a team; a Repo Manager for detail inside its own project. Both reach the same agents, so pick whichever is open.

Two teams want the same issue. Who gets it?

Whoever claimed it first. The other team's engine skips issues with someone else's managed-by: label; agree a hand-off between the managers if needed.

Where do I ask something this guide doesn't answer?

Where the repo's docs/agent-workflow.md says, or ask your agent to load /project-how-it-works.
