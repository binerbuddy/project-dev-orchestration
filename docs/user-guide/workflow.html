pdo Workflow Deep Dive

How one item moves from a report to merged code: every decision point, which skill runs at each step, and which sub-agents that skill spawns. All sub-agents run on Claude Opus by default; a skill may step up to a larger model for unusually high-risk work.

Stage by stage

What each box does

Each sheet lists the skill's steps in order, the sub-agents it spawns (a double-edged chip means several run in parallel), and the points where it stops for a person.

Intake

intake workspace · /project-intake
  1. Classify each item without tools: repo, type, route, a suggested priority, area labels, parent epic.
  2. One bounded, fact-only look for the whole batch: duplicates, related notes and design docs, candidate code locations. No root causes or fixes.
  3. At most one round of questions, only for what the issue can't do without.
  4. Show the drafts as decision points only, then file through pdo file-issue (or comment on a duplicate).
  5. Move worked inbox reports to done/ and tell the reporting agent its issue number.
Explore1 · read-only · ≤15 tool calls
GateFile as drafted, adjust, or drop. Items that could change analysis results, permissions or saved data carry a blocking approval that is never waived.

Orchestrator tick

Orchestrator (<project>) · /project-orchestrate on a loop
  1. Read the watcher's snapshot: events, agents, free slots, usage, queue, conflicts.
  2. Handle each event (table at the end of this page).
  3. Wake agents whose PRs conflict with the base branch to rebase, two at a time.
  4. Fill free slots from the queue: the urgent bypass first, then in rank order, skipping capped repos and anything under the spawn floor. pdo spawn makes the worktree, opens a tab in the project's home workspace, starts the agent and claims the issue.
  5. Re-arm the watcher and report what changed and what waits on a person.

No sub-agents. It starts command agents as separate sessions (one per issue, 3 working at once by default) and never edits product code, merges, or answers agents' questions. The project's Repo Manager starts and stops it on the owner's or the CEO's direction.

Small route

command agent · /project-small-feature-or-bug-fix
  1. Intake questions: behaviour, affected areas, repro.
  2. Explore the code and project notes.
  3. Ambiguity loop, only if needed: batched questions until the design is settled.
  4. Consensus plan: a review panel judges the plan (agree / agree with changes / reject), up to 3 rounds.
  5. Implement in a fresh worktree with checkpoint commits and the repo's compile gate.
  6. Automated QC against the base branch: test, verify, fix, re-test, up to 3 cycles.
  7. Write the QC checklist (and push test data to qc-fixtures).
  8. Changelog, push, draft PR with Closes #n.
  9. One background review cycle: PR review, then review triage with its gates waived.
  10. Stop servers, mark the PR ready, label ready for QC; a final verifier checks plan against result.
Architect · Security · Adversaryplan panel · parallel · + profile roles, UI/UX when there's UI Executorimplementation · where parallel work helps PR review sessionbackground · fans out its own panel Review triage sessionbackground · after the review Verifier1 · read-only · final check
GatesOnly steps 1–3 talk to you. From the plan on, it runs without approval stops. A small issue that turns out to need a migration or a cross-cutting UX call stops and asks to be re-routed.

Design route

command agent · /project-feature-design
  1. Intake: what the feature must do, for whom, and what it must not do.
  2. Design worktree on docs/<slug>-design.
  3. Survey in parallel: the code today, project notes, and a sweep of related issues (umbrella, fixed-by, related, stale).
  4. Draft the doc: phases with dependencies and acceptance criteria, UX gates (at most two, at most one blocking), decisions marked decided / provisional / open.
  5. Panel review of the design, up to 3 rounds; unresolved points become provisional decisions.
  6. Decisions gate with you.
  7. Commit the doc, then create the epic and one epic-phase sub-issue per phase, chained by "blocked by".
  8. Mark the epic route:build: the watcher fires design_ready and the orchestrator starts the build agent.
Search sub-agentscode survey · parallel Architect · Security · Adversary · UI/UXdesign panel · parallel · + profile roles
GateThe only one: you decide the open choices, confirm the provisional ones and the UX gates, decide what happens to related issues, and approve any write to another repo. No product code is written on this route.

Build route

command agent · /project-feature-build
  1. Load and validate the design doc; its decisions and non-goals are pinned into every sub-agent's brief.
  2. Worktree feat/<epic#>-<slug> from the design branch; a committed progress ledger tracks every phase.
  3. Phase loop in dependency order, each phase in its own background session: implement, compile gate, fresh-eyes review of the phase diff, phase QC (up to 3 cycles), verifier, ledger update. One commit per phase, pushed and noted on the phase issue.
  4. At each UX gate: comment on the PR and label the PR and the issue awaiting-ux-gate (yellow: your move). The issue label frees the slot. Blocking gates stop; async gates let independent phases continue.
  5. Finalize: full compile and smoke run, doc marked Implemented, a merged QC checklist, the same review and triage cycle as the small route, a verifier over the whole doc, then ready for QC.
Phase session1 per phase · background Executorinside each phase Code Review · Adversaryper phase · parallel · never told the reasoning Verifierper phase, then once over the whole doc PR review + triage sessionsat the end · as in the small route
GatesConfirm acceptance criteria if the doc lacks them; sign off prototypes at the UX gates the design declared; decide if a spike phase comes back no-go. Nothing else stops for approval.

PR review

background session · /project-pr-review
  1. Check the PR out in a temporary detached worktree and save the diff.
  2. Fan out the reviewers in one go; each writes findings with severity, location, failure scenario and fix.
  3. Deduplicate. Findings several reviewers raised are kept; every other finding goes to three judges, who check it against the code. It survives with at least two of three votes.
  4. Post one review comment, Critical to Low, then remove the worktree.
Architect · Code Review · Security · Adversaryalways · parallel Profile rolese.g. UI designer, data/migration reviewer Judge × 3majority vote per finding

No gate. A person reads the posted review like any other.

Review triage

background session · /project-pr-triage
  1. Gather every review, inline thread and comment into one list.
  2. Rate each finding likely, plausible, unlikely or not-a-fix against the code, and draft a solution.
  3. A panel checks the solutions (not the findings).
  4. Pick fixes. Inside a lifecycle the likely and plausible ones the panel approved are taken automatically.
  5. Implement one commit per fix, run the checks, then a completeness verifier.
  6. Push and post one comment: fixed (with commits) and not fixed (with reasons). New QC steps are added under "Added after review triage".
Traceroptional · for unclear findings Architect · Security · Adversarysolution panel · parallel · + profile roles Executorone per fix group · parallel Verifier1 · read-only
GatesRun on its own, it stops twice: you pick the fixes, then you pass a QC checklist before the push. A lifecycle skill waives both, and its compile and headless QC stand in.

Agent QC

QC Agent (<project>) · /project-agent-qc on a loop
  1. Take the highest-priority ready for QC PR and claim it.
  2. Serve it on the QC Agent's own ports with a database cloned from the seed.
  3. Test: the checklist; the touched screens and their neighbours in a browser; the API, including bad input and the wrong role; two users at once; earlier findings. A repo with no UI runs fixtures and parallel API calls instead.
  4. Fail: post "Agent QC findings (round N)" and wake the PR's agent. The second failure adds QC escalated instead.
  5. Pass: apply the visible-change rule (or the repo's own pass rule). Visible or needs UX review: QC complete - ready to review. Otherwise: Ready for Merge + UX testing skipped.
  6. Tear down, release, and restart with a clean session before the next PR.

No sub-agents. One PR per tick, about an hour each, never on a person's ports or data.

Human QC and UX review

Human Review (<project>) · /project-human-review, or GitHub in a browser
  1. /project-human-review <PR#> serves the PR on the reserved QC ports with its own data. With no argument it lists what's waiting.
  2. Type findings in plain words: they're posted as "QC feedback (round N)" and the agent is woken. From a browser, a Request-changes review does the same.
  3. pass (or the Ready for Merge label) ends QC. If agent QC hadn't already triggered the wrap-up, the agent is told to wrap up now.

No sub-agents. Feedback removes the QC labels, so the fixed PR goes back through agent QC.

Wrap-up and close-out

command agent, then the watcher
  1. At the first QC pass the orchestrator wakes the agent once: last fixes, final push, closing comment, "wrap-up done". It never merges.
  2. A person reviews the code and merges.
  3. The watcher closes the agent's tab, removes the managed-by: claim, and later sweeps temp files. The orchestrator marks the card Done.

What moves work between agents

Watcher events

Agents don't call each other. A token-free script checks every agent, PR and label every 5 minutes, and the orchestrator acts on what changed. Each event fires once.
