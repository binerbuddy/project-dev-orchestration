# project-dev-orchestration

Lifecycle skills and an orchestration engine for running a team of coding agents on a GitHub project.

- **Skills** (`skills/`): tool-neutral Agent Skills for every step from repo setup to merged PR: repo
  setup, intake, feature design, feature build, small fix, PR review, review triage, QC review, status and worktree
  clean-up, plus the System Manager (runs one project's team) and the **CEO**
  (`ceo`: opened first; starts and pauses project teams on your direction and oversees all project managers). Claude Code, Codex and Grok Build can all
  load them. Each skill works on the git repo of the current directory, and reads that repo's
  `.agents/project-profile.md` for its build commands, dev servers, QC data and conventions.
- **Engine** (`bin/`): optional bash and python scripts that run the team unattended. They rank the
  project board, spawn one command agent per issue in its own [herdr](https://herdr.dev) workspace and git
  worktree, watch the agents, hibernate the idle ones, route QC feedback, and keep the board current.

A collaborator needs only the skills. The engine is for whoever runs the team.

## Quick start

**Claude Code**

```
/plugin marketplace add binerbuddy/project-dev-orchestration
/plugin install pdo@project-dev-orchestration
```

or from a checkout: `bin/install --claude`. The skills show up as `/pdo:project-<name>`.

**Upgrading from 0.9 or earlier.** 0.10.0 renamed the plugin from `project-dev-orchestration` to `pdo` (the
marketplace keeps its name). Remove the old one first, or every skill appears twice:

```
claude plugin uninstall project-dev-orchestration@project-dev-orchestration
claude plugin marketplace update project-dev-orchestration
claude plugin install pdo@project-dev-orchestration
```

then `/reload-plugins` (or restart) in open sessions. An engine install set `PDO_SKILL_PREFIX` in `config.env` only
if you changed it; the default is now `/pdo:`. A `pdo` launcher from 0.9.8 follows the old plugin's versions: re-run
`/project-setup repo+team` or `<plugin>/bin/install --bin` to point it at the new one.

**Codex**

```
codex plugin marketplace add binerbuddy/project-dev-orchestration
codex plugin add pdo@project-dev-orchestration
```

or from a checkout: `bin/install --codex`. `bin/install --codex --link` links the skills into
`~/.agents/skills/` instead.

**Grok Build**

```
grok plugin install binerbuddy/project-dev-orchestration
```

Grok reads the Claude plugin layout. From a checkout: `bin/install --grok`, or `--grok --link` to link the
skills into `~/.grok/skills/`.

**The engine** (only if you run the orchestrator) ships inside the plugin. Install the plugin as above, open your
agent in the repo the team will work, and run:

```
/project-setup repo+team
```

It installs the engine from the plugin (`~/.local/bin/pdo`, a launcher that always runs the newest installed plugin
version, so plugin updates need no re-install), checks the requirements below, registers the repo
(`projects/<name>.env`, optionally a board), opens the repo-files PR, and tells you how to start the team
(open a session named CEO and run `/ceo fire up <name>`: it opens the project's Repo Manager with
`pdo start-manager`, which starts its team; or `pdo team-up --project <name>` without one).

To work on the engine itself, or pin a version, use a checkout instead: clone this repo and run `bin/install --bin`
(a symlink to the checkout's `bin/pdo`; it replaces a plugin launcher). `PDO_HOME=<checkout> pdo …` runs a checkout
for one command without changing the install.

Requirements: bash 4+, python 3.8+, git 2.31+, jq, the GitHub CLI (`gh`), herdr, and an agent CLI
(Claude Code today; launching is behind one seam, `launch_agent` in `bin/lib.sh`).

### Setting up a new repo

Step one for any repo that will use the system: open your agent in it and run **`/project-setup`**. It asks
whether an orchestrator team (pdo) will run the repo on this machine: **repo-only** (`/project-setup repo-only`)
adds just the repo files every agent reads; **repo+team** (`/project-setup repo+team`) also registers the repo
with the engine. It decides by itself when the repo is already registered or `pdo` isn't installed. It detects the layout, origin and build commands, drafts
`.agents/project-profile.md` (from `templates/project-profile.md`), adds the "How work flows here"
section (`templates/AGENTS-workflow-section.md`) to `AGENTS.md`, writes the human guide `docs/agent-workflow.md`
(`templates/agent-workflow-guide.md`), gitignores `.agents/local/`, creates the missing GitHub labels,
writes `projects/<name>.env` and optionally wires up a project board, asks only for what it can't
detect, and opens a PR on `chore/agent-workflow-setup`. Re-run it any time: it reports what is present
and what has drifted, and only fills gaps.

### Notes on the skills

- **Install them together, as the plugin.** The skills share reference files through sibling paths
  (every reviewer consortium uses `skills/project-pr-review/references/review-roles.md`; the build
  skill uses the design skill's doc contract and the small-fix skill's QC checklist), and they point at
  `templates/`. A single skill copied on its own loses those links. `bin/install --link` links all of
  them side by side.
- **Skill names.** The skills refer to each other as `/project-<name>` (e.g. `/project-intake inbox`).
  Under the Claude Code plugin a skill may appear namespaced, as
  `/pdo:project-<name>`; both mean the same skill. The engine launches the
  standing agents with `PDO_SKILL_PREFIX` (default `/pdo:`); set it to `/` in
  your `config.env` when the skills are linked un-namespaced.
- **Engine commands** appear in the skills as `pdo <name> …`. Without `pdo` on PATH, run
  `<engine checkout>/bin/<name> …`; a dispatch brief gives agents the absolute path, and a repo's `AGENTS.md`
  names the checkout for sessions a person starts (`bin/install --bin` puts `pdo` on PATH).

## How it fits together

```
 GitHub board + issues ──► queue (ranks: Claude Work This, P1..P4)
                              │
 human ◄── questions ──┐      ▼
   │                   │   orchestrator agent (/loop project-orchestrate)
   │                   │      │ spawn                     ▲ events
   │                   │      ▼                           │
   │             command agent per issue ────────────► watch (token-free poller)
   │             (own herdr tab + worktree,               │ hibernate / close-out
   │              runs a lifecycle skill)                 │
   │                   │ PR labelled "ready for QC"       │
   ▼                   ▼                                  │
 human review (project-human-review) ── serves the PR ── qc ── QC_HOOK (project's servers)
   │ feedback / pass ──► resume-agent ──► same command agent, same session
   ▼
 human merges
 intake agent (project-intake) ◄── intake-submit (reports from every agent)
```

## Configuration

Project config is a bash env file, `projects/<name>.env`, found in the first of `PDO_CONFIG_DIRS`
(colon-separated; default `~/.config/project-dev-orchestration`) that has it. A config dir may also hold
`prompts/` (e.g. your own `dispatch-brief.md`), `hooks/`, and `config.env` (install-wide defaults).

```bash
# ~/.config/project-dev-orchestration/projects/acme.env
ORG="acme"                    # GitHub org (or user) that owns the repos and the board
PROJECT_NUMBER=3              # org project board number
declare -A REPO_ROOT=(        # repo -> local clone root (a bare root holds worktrees as subdirs)
  [widget]="$HOME/src/widget.git"
  [widget-docs]="$HOME/src/widget-docs"
)
PRIMARY_REPO="widget"         # bare "#12" means widget#12
GH_USER="acme-bot"            # optional: pin gh and git (every agent and pdo script) to this login
QC_HOOK="hooks/acme-qc"       # optional: starts/stops your QC servers (relative = this config dir)
QC_PORTS="3000 4200"          # optional: ports hibernation must never stop
WATCH_EVENT_HOOK="hooks/acme-events"  # optional: project-specific watcher events (e.g. PR-comment commands)
```

Every script takes `--project <name>`. Without it they use `$PDO_PROJECT`, else the project whose
`REPO_ROOT` holds the current directory's repo, and otherwise fail with the list of known projects. State
lives in `PDO_STATE_DIR` (default `~/.local/state/project-dev-orchestration`). `pdo project-env` prints a
project's resolved settings, and `pdo project-env --board` its board's ids. A project with several repos can give
each its own fixture format (`declare -A FIXTURE_EXT_BY_REPO=([other-repo]=".dump")`). The full key list and the hook contracts are in
[docs/design.md](docs/design.md#configuration).

## Multiple GitHub accounts

`gh` has one active account for the whole machine, and git over HTTPS (credential helper
`!gh auth git-credential`) follows it. Someone with a work org and personal repos, and agents in
both, breaks the other context every time anything runs `gh auth switch`. The engine's per-project
`GH_USER` pin covers only the agents it launches and its own scripts. `bin/install --gh-identities` covers everything
else, without switching:

1. **A map**, `~/.config/project-dev-orchestration/gh-identities`: one line per GitHub owner (org or
   user), `<owner> <gh-login> [<commit-email>] [<commit-name>]`, plus `default <login>`. `#` starts a
   comment.

   ```
   acme-corp  alice-work  alice@acme-corp.example  Alice Example
   alice      alice       alice@example.com
   default    alice
   ```

2. **A `gh` shim** (`~/.local/share/project-dev-orchestration/shims/gh`, first on PATH). It finds the
   owner (from `-R/--repo`, the `OWNER/REPO` of `gh repo <sub>`, an `api` path `repos/OWNER/` or
   `orgs/OWNER/` or a GraphQL `owner:`/`login:`, `project --owner`, a github.com URL, else the
   current repo's `origin`), and runs the real gh with `GH_TOKEN` set to that login's token
   (`gh auth token -u`, a local lookup). An owner not in the map gets `default`; no default leaves
   the active account. When `GH_TOKEN` or `GITHUB_TOKEN` is already set (the engine's pin, a bot),
   the shim changes nothing. `gh auth switch`, and `gh auth login` without `--hostname`, are refused
   unless `PDO_GH_ALLOW_SWITCH=1`.
3. **Git, per owner.** A generated `gitconfig-identities`, included from your global gitconfig by
   one appended `[include]` line, sets a credential helper per `https://github.com/<owner>` (so
   pushes, fetches and clones use that login's token, whichever account is active) and, through
   `includeIf "hasconfig:remote.*.url:..."` for https and ssh remotes, that owner's `user.email` and
   `user.name`. Nothing else in your gitconfig is changed.

```
bin/install --gh-identities --map ~/my-gh-identities   # or edit the template it writes, then re-run
# add the printed line to your shell profile, open a new shell, then:
pdo install --gh-identities --check                     # owner -> login -> email for this dir
```

Each login must be in gh once (`PDO_GH_ALLOW_SWITCH=1 gh auth login`, then
`PDO_GH_ALLOW_SWITCH=1 gh auth switch` back to your usual account). Re-run the install after editing
the map or updating the engine (the shim and the helper are copies). `--dry-run` shows what it would
do; `--uninstall` removes the shim, the helper, the generated files and the include line, and keeps
the map. Per-owner `user.email` needs git 2.36+. `sysreport` and `fleet` show whether the shim is
active and the map's owners. `PDO_GH_SHIM=off` makes the shim a plain pass-through for one command.
